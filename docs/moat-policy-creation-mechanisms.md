I’ll explain how Moat actually works internally with OPA bundles, because this is the key mechanism most people misunderstand.

Moat itself does not evaluate policies.
Moat is a policy control plane that:
	1.	Stores policies
	2.	Organizes them
	3.	Compiles them
	4.	Packages them into OPA bundles
	5.	Distributes those bundles to OPA agents

Then OPA executes the policies.

⸻

1. Core Moat Architecture

The architecture looks like this:

Policy Author
     │
     ▼
Moat Policy Registry
     │
     ▼
Policy Compiler
     │
     ▼
Bundle Builder
     │
     ▼
OPA Bundle Server
     │
     ▼
OPA Agents (runtime evaluation)

Moat’s main responsibility is building the bundle.

⸻

2. What an OPA Bundle Actually Is

An OPA bundle is just a tarball (or directory) containing:

bundle.tar.gz
   ├── policy/
   │      authz.rego
   │      geography.rego
   │      classification.rego
   │      role.rego
   │
   ├── data/
   │      datasets.json
   │      users.json
   │      roles.json
   │
   └── manifest.json

OPA downloads this bundle periodically.

Example:

GET /bundles/authz

OPA reloads policies automatically.

⸻

3. How Moat Organizes Policies

Moat groups policies into policy packages.

Example:

authz/
   role_policy.rego
   geography_policy.rego
   classification_policy.rego
   regulatory_policy.rego

Each policy is a rego module.

Example:

package moat.authz.role


⸻

6. How Policies Are Evaluated

OPA evaluates the entrypoint policy.

Example entrypoint:

package moat.authz

default allow := false

allow if {
  data.moat.authz.role.allow
  not data.moat.authz.geo.deny
  not data.moat.authz.regulatory.deny
}

So evaluation becomes:

Role policy → allow
Geo policy → check deny
Regulatory policy → check deny


⸻

7. How Multiple Policies Are Combined

This is the critical point.

OPA does not enforce order.

Instead you combine policies in the entrypoint rule.

Example:

allow if {
   role_allow
   not geo_deny
   not regulatory_deny
}

Where:

role_allow := data.moat.authz.role.allow
geo_deny := data.moat.authz.geo.deny
regulatory_deny := data.moat.authz.regulatory.deny

10. When You Have Many Policies

The correct pattern is policy layering.

Example folder structure:

bundle/

  regulatory/
     sanctions.rego
     compliance.rego

  classification/
     pii.rego
     phi.rego

  geography/
     residency.rego

  entitlement/
     role.rego
     group.rego

  resource/
     dataset_policy.rego

  main.rego

main.rego becomes the policy orchestrator.

⸻

11. Example Main Orchestrator Policy

package moat.authz

default allow := false

allow if {
   entitlement_allow
   not regulatory_deny
   not geography_deny
}

entitlement_allow := data.moat.authz.entitlement.allow

regulatory_deny := data.moat.authz.regulatory.deny

geography_deny := data.moat.authz.geography.deny

12. How Netflix and Large Companies Do It

They split policies into dimensions.

policy_dimensions

  regulatory
  classification
  geography
  entitlement
  resource

Each dimension outputs:

allow
deny
constraints

Then one orchestrator combines results.

⸻

13. Why This Is Important

Without orchestration you get:

policy conflicts
unpredictable results
unexplainable decisions

With orchestration you get:

deterministic decisions
policy governance
clear precedence
auditability


⸻

14. What You Should Do For Your Platform

Since you are building Moat + Trino + OpenMetadata governance, your bundle should look like:

bundle/

dimensions/

   regulatory/
   classification/
   geography/
   entitlement/
   resource/

   decision.rego

OPA only queries:

data.moat.authz.allow

Everything else stays internal.
